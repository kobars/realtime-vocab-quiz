## PR-104 — Deliver published broadcasts to store subscribers

- **Tool:** Claude Code (claude-opus-5-5); Codex CLI (`gpt-6-astra`, extra-high reasoning) for a read-only analysis of the store layer before the PR
- **Task:** Add a feed port beside the store port: `subscribe(quiz_id)` yields each published `events` message (`{"frame": …, "ranks": …}`). The Redis store subscribes to the quiz's `events` channel; the memory store publishes the same message from `publish_if_dirty` and `end_quiz`, with the ranks of scorers outside the top N above `full_list_max` players.
- **Prompt / interaction:** The agent read `docs/spec/redis.md` §2, §3 and §5 and the `publish_leaderboard` and `end_quiz` scripts, wrote the port, both adapters and one integration test that runs on both stores. A second model then analyzed the store layer read-only (parity between the two stores, the feed's lifecycle, spec drift, duplication); each of its findings was checked against the code before any change.
- **What was wrong or changed:**
  - The first version of the Redis `subscribe()` ignored the result of `get_message(timeout=5)`: with no confirmation it entered anyway, so "subscribed once entered" did not hold. It now raises `ConnectionError`; `test_unconfirmed_subscription_is_unreachable_and_closed` catches it.
  - Errors raised while the feed was read escaped as redis-py exceptions, unlike every script call, which maps them to the built-in `ConnectionError` and `TimeoutError`. The feed's read loop now runs inside the same mapping; `test_a_dropped_feed_raises_the_builtin_connection_error` catches it.
  - The memory store copied the service's row-to-entry helper and encoded frames with `encode` instead of `encode_broadcast`. `Row.entry()` is now the one conversion, and the memory store uses `encode_broadcast`.
  - Review before the merge found two more mistakes. The memory store kept its feeds on the quiz record, so `subscribe()` on a quiz it did not know raised `QUIZ_NOT_FOUND` while Redis subscribed silently; feeds are now kept per quiz id on the store, and `test_a_subscription_before_the_quiz_exists_gets_its_broadcasts` runs on both stores. Neither store closed the yielded iterator on exit, so a read after exit blocked forever on the memory store; both now close it (`aclosing`), and `test_a_read_after_leaving_ends_the_feed` times out on the memory store without the fix.
  - Review cleanups: one helper picks a frame's entries for both `snapshot()` and `publish_if_dirty()`, the Redis confirmation timeout is a named constant, and the feed tests bound every read with `wait_for`, start Redis only for the Redis case and check that a second frame carries no ranks when nobody scored since the first.
  - Not changed, by design: the memory store's per-subscriber queues are unbounded (single-process twin; the gateway's send buffer limits apply per socket), and the order of `ranks` differs between the stores (rank order in memory, set order in Lua), which no consumer relies on.
- **Verification:**

  - `api/tests/unit/adapters/test_redis_feed.py`: both tests fail without the confirmation check and the error mapping.
