## PR-121 — Ranks-only standings read, a waiting Redis pool and full leaderboard conflation

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Fix three verified performance findings of a whole-codebase analysis: snapshots that transferred the broadcast rows they threw away and refilled the cache once per concurrent miss, a Redis pool that failed at once above 100 concurrent calls, and leaderboard conflation that replaced only the last queued frame.
- **Prompt / interaction:** The agent worked from the verified findings with their evidence, wrote or tightened one test per finding first, confirmed each fails on `main`, then changed the Lua script, the store, the use case, the composition root and the sender.
- **What was wrong or changed:** (1) The AI-written `ranks_of` read `read_standings` with limit 0, which always builds the broadcast rows, and the snapshot use case read a one-row page for its cache key besides; `read_standings` now takes limit -1 for the asked users alone, `Ranks` carries the status, and the cache is keyed on that one read, with concurrent misses sharing one standings read. (2) The composition root left the Redis pool at redis-py's default, which raises `MaxConnectionsError` above 100 connections instead of waiting: a 300-join burst on `main` returned 200 `UNAVAILABLE`; the client now uses a `BlockingConnectionPool` with `REDIS_MAX_CONNECTIONS` and `REDIS_POOL_TIMEOUT_MS`. (3) The sender popped only the last queued `leaderboard` when conflating, so frames queued below the soft limit still went out ahead of the newest; it now replaces the whole run since the last barrier. While writing the fix, the first expectation for the conflation test assumed the buffer stays above the soft limit after a collapse; it drops below it, so the next frames queue normally after the rebased one, and the test now asserts that sequence.
