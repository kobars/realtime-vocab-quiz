## PR-140 — Test exact store limits and the gateway frame size boundary

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Add tests at the exact limits where the memory store and the Redis Lua scripts could drift: a snapshot at `FULL_LIST_MAX` and `FULL_LIST_MAX + 1` players, the Lua deadline check at the deadline ms itself, a question served closer to the deadline than its time limit, a quiz start ahead of the server clock (the reached-time clamp), and a gateway frame of exactly `max_payload` and `max_payload + 1` bytes.
- **Prompt / interaction:** The agent worked from a list of boundaries and the source lines behind them. It wrote the contract cases over both stores, added a `move_start` step to the contract harness, replaced the far-above-limit gateway case with an exact-boundary one, then applied one mutant at a time in a scratch worktree (`>=` to `>` on the Lua deadline check, `<=` to `<` on `full_list_max`, the reached-time clamp and the remaining-time cap removed, `>` to `>=` on the gateway size check) and confirmed each makes a new case fail.
- **What was wrong or changed:** Two mistakes in the AI output, both fixed on this branch. First, the deadline case relied on the Redis `pass_deadline`, which read `TIME` and wrote `deadlineMs` in two round trips; only about 1 in 20 following scripts read the same ms, so with 50 tries the `>=` to `>` mutant still survived 1 run in 15. Repeating the mutant run showed it; `pass_deadline` now writes the server's `TIME` in one script, about every other try lands on the exact ms, and the mutant failed 20 runs out of 20 with 30 tries. Second, the start-ahead case indexed the `ranks_of` rows, which are optional per user, so mypy failed in `make check`; the case now reads the order from a standings page. The review before the merge found three more, fixed on this branch. Third, the near-deadline serve case and the deadline case created quizzes with a 100 ms window, so on Redis a stall of 100 ms during `join` or `serve_next` would have failed them with `QUIZ_ENDED` before any assertion; the serve case now uses a 5 s window, far below the 20 s limit and far above any setup step. Fourth, the deadline case still caught the `>=` to `>` mutant only when the round trip after `pass_deadline` stayed under 1 ms, so on a slower runner the mutant would survive a green suite; the Lua check is now pinned without timing by a composed script that calls `check_player` at the deadline and one ms before it, and the timing-bound contract case is gone (the Python side is pinned in `api/tests/unit/test_session.py`). Fifth, the harness deadline script repeated the server's ms formula; it now calls `now_ms()` through `compose`.
- **Verification:** `make check` (exit 0). `make test-integration`: 165 passed. The cases are in `api/tests/contract/test_store_contract.py` and `api/tests/integration/ws/test_gateway.py`; the size, standings and remaining-time mutants each fail a case there, and the deadline mutant fails `test_check_player_ends_the_quiz_at_the_deadline_ms_itself` in `api/tests/integration/test_script_loader.py`. `scripts/check_internal.py --commits origin/main..HEAD` is clean.
