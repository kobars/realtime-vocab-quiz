## PR-145 — Serve one quiz from two nodes: resubscribe with backoff and repair snapshots

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Make two API nodes on one Redis act as one for a quiz: the fan-out loop subscribes again with full-jitter backoff after any subscribe, feed or tick failure, sends each local player a snapshot after the resubscribe, skips queued frames the snapshots hold, and treats a silent redis-py pub/sub reconnect as a drop; prove it with a two-node integration test.
- **Prompt / interaction:** The agent read the fan-out loop, the relay and redis-py's pub/sub client, found that redis-py reconnects and subscribes again without telling the caller, and made the Redis feed raise on that second confirmation. It then wrote the two-node test with two uvicorn apps in one event loop and real protocol clients, and checked that the pub/sub kill test fails on `main`.
- **What was wrong or changed:** In the first version of the two-node test, the pub/sub kill test sent an answer through the client after the kill, and the unasked repair snapshot was taken as the reply to `next` (a `KeyError` on `score`); the change after the repair now goes through the store. The first seq check reset its count at the resync's snapshot and failed when a frame published during that read arrived before the snapshot; it now tracks the newest seq seen, which is what the test is meant to prove (frames relayed in order, no gap). A fault test merged meanwhile asserted the old behavior, a loop that stops for good after a refusal; it now expects the new subscription and the snapshot. The first draft was above the 400-line budget: the convergence check joined the delivery test, and a store-level resubscribe test that the fault suite and the pub/sub kill test already cover was dropped. The review before the merge found four defects in the first version of the loop: a quiz lost during the drop made the repair's read raise `QUIZ_NOT_FOUND`, which the loop retried forever instead of stopping (now the loop stops on it from any step); the backoff counter was reset right after the repair, so a failure that recurred while serving never backed off past the first step and sent snapshots every round (now it resets only after a relayed broadcast or a tick that went through); each player's repair snapshot was read on its own, so players could get different `atSeq` values while the relay skipped up to the newest one, leaving a gap for the others (now one rank read and one standings read serve every player at one seq, which also replaces N sequential reads); and the relay kept its pre-drop rank state, so after a store restart that moved `seq` back it sent no shifted `rank_update` until `seq` passed the old value (now the repair resets that state from the snapshots' ranks). A spec line also cited a test that did not exist.

  - `api/tests/unit/fanout/test_tick_faults.py`: a refusal from the tick logs its traceback, the loop subscribes again and sends the snapshot; `test_a_quiz_lost_during_the_drop_ends_the_loop_at_the_repair` and `test_the_backoff_grows_until_a_tick_goes_through` catch the first two review findings.
  - `api/tests/unit/app/test_service.py::test_standings_read_every_player_at_one_seq` (one seq for every repair snapshot, one rank read per try) and `api/tests/unit/fanout/test_broadcast_bounds.py::test_a_repair_at_an_older_seq_tracks_ranks_from_the_snapshots` (rank tracking after `seq` went back) catch the other two.
