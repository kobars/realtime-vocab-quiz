## PR-15 — Add the strict inbound frame parser and the broadcast encoder

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Add `parse_client_message`, which checks the frame size and the JSON nesting depth on the raw bytes before parsing, then the version and the type, and returns a typed client message or the protocol error to send back; and `encode_broadcast`, which encodes each broadcast once for the fan-out.
- **Prompt / interaction:** The agent built the parser from the error-code table and the limits in `docs/spec/protocol.md`, wrote one test per rejection rule plus a Hypothesis encode-then-parse property, and rebased the change onto the merged message models before opening the PR.
- **What was wrong or changed:** The parser and its tests were first written in the same change as the message models, which went over the 400-line limit per PR; they were split into this PR and rebased onto the merged models with no code changes. The post-merge review found two mistakes in the parser, both fixed in a follow-up PR: integer fields had no upper bound, so an `offset` of 10^30 or a 4000-digit `questionIndex` parsed as a valid message instead of `INVALID_MESSAGE` (spec section 7, "wrong type or range"); and the missing-`v` and wrong-version errors returned a null `requestType` even when the frame named a known client type (spec section 2.4). The tests that now catch them are `test_an_integer_above_the_wire_maximum_is_an_invalid_message` and `test_a_version_error_names_a_known_request_type` in `api/tests/unit/contracts/test_codec.py`.
- **Verification:** `make check` (exit 0; 179 tests). Tests: `api/tests/unit/contracts/test_codec.py` (size and depth at and above the limit, brackets inside strings, malformed frames, wrong versions, unknown types, version checked before type, compact broadcast encoding) and `api/tests/unit/contracts/test_roundtrip.py` (encode then parse returns the same message).
