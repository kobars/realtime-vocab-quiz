## PR-167 — Resend a join that gets no reply, and keep one retry timer per answer

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Close two gaps in `QuizClient` (`web/src/protocol/client.ts`): a `join` that the token bucket drops was never sent again (no reply deadline, no retry after a `RATE_LIMITED` that names no request), and an answer's retry after `RATE_LIMITED` or `UNAVAILABLE` was not tracked, so a `joined` arriving while it waited sent the same answer twice and put its `submissionId` in the in-flight list twice.
- **Prompt / interaction:** The agent got both defects with the code paths involved, wrote the tests first with fake timers (six of the eight new tests failed on the previous client), then gave `join` one timer like `resync` and replaced the answer deadline map with one timer per answer that sending the answer replaces.
- **What was wrong or changed:** (1) The first draft of the duplicate-answer test dropped the socket and took the newest socket at once, before the reconnect backoff had opened a new one, so it asserted on the old socket; it now waits for the reconnect and checks that a second socket exists. (2) The existing test `keeps an answer after NOT_JOINED, joins again and resends it after the next joined` checked the frames after `joined` at a fixed position; the new 5 s join resend shifts them, so it now checks the last two frames. (3) The first version of `retryAnswer` left a fired timer in `answerRetries` when the resend found the client not joined; the timer callback now removes its own entry, so the map holds only pending timers, as its comment says.
  The review before the merge found four more agent mistakes, fixed in this PR. (4) The new join reply deadline resends a join that was only slow, and the client handled its second `joined` like the first: a second resync less than 1 s after the first, which the server refuses with a `RATE_LIMITED` notice, and a second `joined` event for the UI. A `joined` with no join in flight is now ignored; the client test `ignores the joined of a join sent again while the first was only slow: one resync, one joined event` catches it, and the store test `reconnect: resends the pending answer, ...` now sends the rejoin it expects a `joined` for. (5) An `UNAVAILABLE` reply to such a second join, after the first got `joined`, was dropped, so the UI kept "Server busy" for `join` with no `joined` to clear it; it is sent again after the backoff, as before this PR, and `sends the join again after UNAVAILABLE for a second join whose first already got joined` catches it. (6) A bucket `RATE_LIMITED` moved a join waiting on its `UNAVAILABLE` backoff to a 1 s resend, although the bucket cannot have dropped a join that was not sent; `keeps the backoff of a join after UNAVAILABLE when a RATE_LIMITED names no request` catches it. (7) The edited test `keeps an answer after NOT_JOINED, ...` checked only the last two frames; it checks every frame after `NOT_JOINED` again.
