## PR-168 — Run the bot swarm in Compose and record the measured load runs

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Run the bot swarm as a container in the Compose network (`load/Dockerfile`, the `load` profile in `compose.yaml`, `make load`), add the tooling for the measured runs (a generated many-quizzes bank in `load/gen_bank.py` with its override `load/compose.bank.yaml`, and an API-node sampler in `load/node_stats.py`), run one hot quiz on one node (1,000 and 2,500 bots) and two nodes (5,000) and 500 quizzes of 10 players on two nodes, commit the result files in `load/results/`, tabulate them in `load/README.md`, and fill the measured numbers of DESIGN.md §1 and §9.
- **Prompt / interaction:** The agent started from an earlier container draft, wrote the tests of the two new tools first, ran the four runs against the composed stack (each 180 s of answering after a 30 s ramp, on a flushed Redis and restarted nodes), and wrote the tables and the verdict from the result files.
- **What was wrong or changed:** (1) The container draft copied only `load/bots.py` and `load/latency.py` into the image, but `bots.py` now imports `load/player.py`; the image would have failed at start. The Dockerfile copies all three. (2) The draft's `load` service joined no network, but the full stack now runs on its own `stack` network, so the swarm could not have resolved `nginx`; the service joins `stack`. (3) The first draft of `load/tests/test_gen_bank.py` read the bank's questions as `word`, `answer` and `id`, the JSON file's names, instead of the port's `prompt`, `correct_choice` and `question_id`; mypy rejected it. (4) `node_stats.mib` first silenced mypy on an unmatched size with a `type: ignore`; it now raises `ValueError`, tested in `load/tests/test_node_stats.py`. (5) The first set of the four runs was measured before a rebase brought in a server change (the presence renew loop); the runs were repeated on the rebased code, and `load/README.md` gives the earlier p99s (205, 409, 436 and 313 ms) as a measure of the run-to-run spread. (6) The swarm image ran as root, which the CI's `trivy config` job rejects (a Dockerfile with no non-root `USER`, and none with no `HEALTHCHECK`); the image now sets `USER 10001:10001` and `HEALTHCHECK NONE` (a run is a batch job), and `make load` runs it as the host user, so its result files in the bind-mounted `load/results/` belong to that user. Found while preparing the runs: each quiz a node serves holds one pooled Redis connection for its subscription, so the default pool of 100 cannot serve 500 quizzes on one node; `load/compose.bank.yaml` raises `REDIS_MAX_CONNECTIONS` for that run.
- **Verification:** `make check` (exit 0; 599 pytest, 13 acceptance and 364 Vitest tests); `trivy config .` finds nothing in the three Dockerfiles; a `make load` run wrote its result file as the host user; the four runs are valid (no swarm process above 80% of a core, no missing or timed-out sample) with leaderboard p99s of 206, 359, 379 and 233 ms; tests `load/tests/test_gen_bank.py` and `load/tests/test_node_stats.py`.
