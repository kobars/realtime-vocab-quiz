## PR-179 — Explain every connection and session state in the web client

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Make each connection and session state of the Vue client either recover by itself or tell the player what to do. The changes: a first join that gets `UNAVAILABLE` is retried with a "Server busy, retrying" line instead of failing. A first join that ends blocked shows the blocking card with its action. The store owns `online`, `waiting` and `requested`, so Start, Skip and Next question are `aria-disabled` while the socket is down and `aria-busy` while their `next` is pending. `QUIZ_NOT_FOUND` after the join shows "This quiz is no longer available." with a Back to join link. A rejoin on an open question shows a "Loading the question…" card. A refresh of `/quiz/:quizId` joins the quiz again. The join screen links back to a quiz the tab is still in.
- **Prompt / interaction:** The agent read the store, the socket client, the views and `docs/spec/ui.md`. It then changed the store, the views and the spec together, and added one Vitest test per behaviour change through the real `QuizClient` on a fake socket (store) or a mocked client port (views).
- **What was wrong or changed:**
  1. Three existing tests encoded the old behaviour and were changed with it: `web/src/stores/quiz.test.ts` expected a first-join `UNAVAILABLE` to stop the client; `web/src/views/JoinView.test.ts` expected "Could not join, try again" after close 1008 and after 10 failed connects; `web/src/views/PlayView.test.ts` expected `QUIZ_NOT_FOUND` during play to leave the question on screen.
  2. While writing the rejoin after a refresh, the agent found that `store.join` set `connection = 'connecting'` before it created the client. A client that cannot be created (blocked `sessionStorage`) then left a join that looked in progress, which the join screen's new "join already under way" check would have shown as an endless spinner. The store now creates the client first (`web/src/stores/quiz.test.ts`, "a client that cannot be created leaves the store idle…").
  3. Review found four AI mistakes, fixed in this PR, each with a test that fails without its fix:
     - The saved join was written on every `joined`, and browsers copy `sessionStorage` into a duplicated tab, so a duplicate rejoined by itself and took the session from the original tab. The join is now saved only on `pagehide` and read once by the next page (`web/src/stores/quiz.test.ts`, "a duplicated tab, which copies sessionStorage while the page stays open, does not join…" and "the saved join is read once…").
     - The join screen detected a reload rejoin at setup from the connection state, and its outcome watcher was not immediate. The route guard starts the join before the lazily loaded screen opens, so a `joined` that arrived first was never handled. The store now flags a resumed join (`takeResume`) and the watcher runs at once (`web/src/views/JoinView.test.ts`, "a reload whose join ends before the lazily loaded join screen opens still opens the quiz").
     - "Try again" on a blocked first join retried the original quiz ID but opened the route of the ID edited in the form, which redirected back and left "Joining…" on screen. The screen now follows the store's quiz ID (`web/src/views/JoinView.test.ts`, "Try again on the blocking card joins the quiz that was sent, even after the quiz ID was edited").
     - The "Loading the question…" card was a `role="status"` region inserted with its text, which screen readers often do not announce. A status region now stays in the page and the card is plain (`web/src/views/PlayView.test.ts`, "a join on an open question shows a Loading the question card, announced by a status region…").
     Cleanups from the same review: `requested` is a boolean (no reader used the index), `resume` returns nothing, the 10-connects block goes through `setBlocked`, and `docs/spec/ui.md` says the next buttons are locked in every state but `resyncing` and `live`.
