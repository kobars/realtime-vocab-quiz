## PR-185 — Run the stack on a public VM behind HTTPS with Caddy

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Add `compose.prod.yaml`, an override of `compose.yaml` for a public Linux VM. Caddy publishes 80 and 443, gets a certificate for `DOMAIN` (Let's Encrypt, or its local CA with `TLS_ISSUER=internal`) and proxies to nginx over an `edge` network. nginx publishes no port and trusts `X-Forwarded-For` from the edge subnet only (`infra/nginx/real-ip.conf.template`). Also: `.env.prod.example`, `make prod-up`, `prod-down`, `prod-logs` and `prod-demo`, the "Deploy to a VM" section of `docs/operations.md`, and a CI job that runs the system tests over HTTPS and wss.
- **Prompt / interaction:** The agent read the edge config, the API's address checks (`api/src/quiz/adapters/ws/limits.py`) and the nginx image's entrypoint before it chose a design. It brought the override up locally with Caddy's local CA and ran the system tests through it. It then turned the real-ip directives off to confirm that the new two-address test fails without them.
- **What was wrong or changed:** The first change to the `containers.yml` compose step put both `docker compose config` commands in one multi-line `run:` block. `scripts/tests/test_repo_config.py::test_container_workflow_runs_every_infra_check_on_pull_requests` reads one-line `run:` steps only, so it failed in `make check`. The step was split into two one-line steps, one per compose file set. The old step had run `docker compose -f <file> config` on each root `compose*.yaml` alone, which would have failed on the override; that was replaced before the first run. The first run of the new `prod` CI job failed before any test ran. The job set `SSL_CERT_FILE` to Caddy's root certificate alone, so uv no longer trusted GitHub's certificate when it downloaded Python (`invalid peer certificate: UnknownIssuer`). The job now sets `SSL_CERT_FILE` only on the test step, to the system CA bundle with Caddy's root appended. That job is the check that catches it.
- **Verification:** `make check` (exit 0; 762 pytest, 13 acceptance and 656 Vitest tests). On the stack started by `make prod-up` with `DOMAIN=localhost` and `TLS_ISSUER=internal`, `make test-system STACK_URL=https://localhost` gave 9 passed. `api/tests/system/test_edge.py::test_two_client_addresses_behind_the_proxy_get_two_session_buckets` failed with the real-ip directives commented out. Without the override, `make test-system` gave 7 passed and 2 skipped. Static checks: `scripts/tests/test_full_stack.py`.
- **Mistakes found in review and fixed:** (a) Caddy's error log wrote a failed request's `X-Admin-Token` header and its `/ws?ticket=` query verbatim (checked with a sentinel token against a closed upstream); the Caddyfile now filters both, caught by `scripts/tests/test_full_stack.py::test_caddy_keeps_the_admin_token_and_the_socket_ticket_out_of_its_logs`. (b) Caddy ran as root, the image's default; it now runs as `65532:65532`, caught by `::test_caddy_is_hardened_and_never_on_the_stack_network`. (c) `git pull && make prod-up` left nginx and Caddy on their old bind-mounted config; `prod-up` now recreates both, caught by `::test_prod_up_recreates_the_edge_so_a_pulled_config_change_applies`. (d) The other make targets ran plain `docker compose` without the override on the VM; `.env.prod.example` now sets `COMPOSE_FILE`, caught by `::test_the_public_host_example_env_names_the_origin_and_the_default_cap`. (e) Real-ip turned nginx's stack-wide `identity` and `api_conn` ceilings into per-client limits; both zones now key on one constant, caught by `::test_the_edge_ceilings_hold_for_the_whole_stack_behind_any_proxy`. (f) `api/tests/system/test_edge.py` failed instead of skipping against an HTTPS stack without a local Caddy container. (g) The `prod` CI job wrote its own `.env` instead of the shipped example, and `scripts/check_nginx.sh` never rendered the real-ip template; caught by `::test_the_https_ci_job_starts_from_the_example_env` and `scripts/tests/test_image_scripts.py::test_the_nginx_check_also_runs_with_the_real_ip_template_rendered`.
