## PR-187 — Wait out the Redis clock skew in the store contract's real-clock harness

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Stop the Redis run of `test_publish_lag_runs_from_the_first_change_the_frame_carries` from failing now and then: it read a lag of 197 ms against a lower bound of 200 ms.
- **Prompt / interaction:** The agent got the failing assertion and its value, traced the 200 ms to host-clock sleeps while `publish_leaderboard.lua` measures the lag on Redis `TIME`, and measured the gap between the two clocks with a probe of 400 sleeps of 200 ms. The review then moved the allowance from the one assertion into the real-clock harness.
- **What was wrong or changed:** The original test, also AI-written, compared a span on the Redis clock with a bound taken from sleeps on the host clock and allowed no gap between the two. The first fix in this PR lowered that one bound by 20 ms. It left the same race in `test_tick_token_holds_at_most_200_ms_after_a_clock_step_back`, which waited `retry_ms + 1` for a key that expires on the Redis clock, and in the sweep-window test, which waits `advance(window)`. Its comment also gave millisecond truncation as the cause, which explains at most 1 ms. Now `real_advance` in `api/tests/contract/conftest.py` sleeps `CLOCK_SKEW_MS` (20 ms) past every forward step, so every assertion keeps its exact bound, and a step back does not wait. `api/tests/contract/test_real_clock_harness.py` now catches a harness that sleeps only the step.
- **Verification:** the publish-lag and tick-token tests ran 100 times in a row on Redis with `uv run --locked --with pytest-repeat pytest --count 100` (all passed); `make check` (exit 0); `make test-integration` (exit 0); test `api/tests/contract/test_real_clock_harness.py`.
