## PR-207 — Fail over from a killed API node in 250 ms instead of 2 s

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** After a hard kill of one API node, clients waited about 2 s, the full `proxy_connect_timeout`, before nginx tried the other node, and some `POST /api/tickets` got 504 after 2 s. Shorten the edge's connect timeout, decide whether the two identity POSTs need a retry on the other node, and measure both effects on an isolated two-node compose stack.
- **Prompt / interaction:** The task came with a suggested fix: a shorter connect timeout, plus `proxy_next_upstream ... non_idempotent` on `POST /api/sessions` and `/api/tickets`. The agent measured first. nginx's error and access logs, and nginx's round-robin source, showed that the 504s came from connects that were never sent. They failed because the resolver dropped the killed node's name while they waited, not because POST is non-idempotent. A test run with `non_idempotent`, `proxy_next_upstream_tries 2` and `proxy_next_upstream_timeout 1s` still gave 11 and 12 504s, against 12 without them, so the PR changes only the timeout. The reason is in `DESIGN.md` §11 and the PR text.
- **What was wrong or changed:**
  - The first load script sent tickets from 8 workers in a closed loop. A worker stuck on the dead node sends nothing more, so the 504 count was capped at 8 and could not show the effect of the timeout → the counts matched the worker count exactly → replaced by an open loop of 100 requests a second, where the count followed the timeout (93 against 12).
  - The first version cut the timeout on the Fly edge too, with a comment about Fly's proxy that was never measured. There, nginx has one upstream server, the Flycast address (ADR-014), so a connect that times out cannot fail over, and the shorter timeout could only turn a slow connect into a 504 → found in review → the Fly edge keeps 2 s, now a pinned difference between the two edges (`scripts/tests/test_fly.py`).
  - Two asserts on the Fly timeout repeated what the line-by-line comparison of the two edges already checks → found in review → removed (`scripts/tests/test_fly.py`).
- **Verification:** `make check` (exit 0); `scripts/check_nginx.sh` on the built web image (successful); `scripts/tests/test_full_stack.py::test_a_killed_node_holds_a_request_a_quarter_second_before_the_other_node` failed before the change and passes after it, as does `scripts/tests/test_fly.py::test_the_fly_edge_is_the_vm_edge_with_only_the_fly_lines_changed` with the Fly line pinned; three kill rounds before and after on an isolated stack (numbers in the PR).
