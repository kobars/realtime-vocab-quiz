## PR-46 — Web protocol client: answer retries with one submissionId

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Add `QuizClient.answer(questionIndex, choiceIndex)` in `web/src/protocol/client.ts`: one `crypto.randomUUID()` per answer, sent at once while joined or held until `joined`; unsettled answers resent with the same `submissionId` after the `resync` that follows each `joined`; a 1 s retry after `RATE_LIMITED` or `UNAVAILABLE`; every other answer error final; errors matched to the oldest answer in flight on that socket. Vitest tests on the fake socket and fake timers.
- **Prompt / interaction:** The agent wrote 13 tests first from protocol spec §2.1 and §7 and saw them fail, then added the client code; it then removed each rule from the client in turn to confirm that a test fails without it.
- **What was wrong or changed:** The mutation pass found one rule with no test: keeping the in-flight list across a reconnect still passed every test, although a stale entry would then absorb an error meant for an answer sent on the new socket. A 14th test now covers it and fails with that mutation. The tests stub `crypto.randomUUID` with `vi.spyOn`, so `afterEach` now restores all mocks.
- **Found after the merge:** The post-merge review confirmed four retry mistakes in the generated client, all fixed in a follow-up PR with tests in `web/src/protocol/client.test.ts`. (1) A token-bucket `RATE_LIMITED` arrives with `requestType: null` (protocol spec §2.4, §9), and the client matched answer errors only by `requestType === 'answer'`, so a dropped answer was never retried; caught by "resends every answer in flight 1 s after a RATE_LIMITED that names no request". (2) That dropped answer stayed at the head of the in-flight list, so the next answer error settled it instead of its own answer; caught by "settles only its own answer with a final error that follows a RATE_LIMITED that names no request". (3) `NOT_JOINED` was treated as final and deleted the answer, although §7 says to join and repeat the request; the test that locked this in was wrong too. Now caught by "keeps an answer after NOT_JOINED, joins again and resends it after the next joined". (4) `UNAVAILABLE` retried after a fixed 1 s instead of the full-jitter backoff; caught by "sends the same answer again after a full-jitter backoff that grows with each UNAVAILABLE".
