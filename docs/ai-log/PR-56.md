## PR-56 — Retry next after RATE_LIMITED and UNAVAILABLE

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Make `QuizClient.next()` in `web/src/protocol/client.ts` resend a dropped `next` with the same index: 1 s after `RATE_LIMITED` (also with `requestType: null`, the token-bucket case) and after the full-jitter backoff after `UNAVAILABLE`, until `question` for that index, `finished` or a final error. A newer `next` or a disconnect cancels the retry; after `NOT_JOINED` the client sends `join` again.
- **Prompt / interaction:** The agent wrote the retry from protocol spec §2.4, §7 and §9 and ui spec §3.7 and §4.3, added Vitest tests on the fake socket and fake timers, and removed each rule from the client in turn to confirm that a test fails without it.
- **What was wrong or changed:** The tests for the final errors, a newer `next` and a disconnect first passed on `main` too, because `main` never retried a `next` at all. Each now also receives a request-less `RATE_LIMITED` after the event, so it fails when the client forgets to clear the pending `next` (checked by removing the clear, the cancel on a newer `next`, and the index match on `question`). The first version treated `NOT_JOINED` as final without joining again; protocol spec §7 says to send `join` and repeat, so it now calls the same rejoin path as the answer retries.
