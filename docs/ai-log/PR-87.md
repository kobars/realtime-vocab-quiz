## PR-87 — Fix failed joins, name length, blocked storage and caret on the join screen

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Fix the five defects that the post-merge review of the join screen (PR-64) confirmed: a failed join that left the form locked, a native name `maxlength` stricter than the rule, a blocked `sessionStorage` that stopped the screen from rendering, a name count without NFC, and the quiz ID caret jumping to the end.
- **Prompt / interaction:** The agent worked from the verified review findings, wrote one failing test per finding first (store, screen and rule tests), confirmed each failed for the stated reason, then made the smallest change that passes them.
- **What was wrong or changed:** The first cut put the caret fix in its own commit after the commit that added its test, so that intermediate commit would have failed `make check`; the two commits were folded into one before the push. The failed-join outcome moved into the store (a failed first join now stops the client and returns to idle), so the screen no longer leaves an unjoined socket open while the form waits for a retry. `docs/spec/ui.md` §3.1 now states the failure message and the NFC count. A later whole-codebase review found one AI mistake: only a failed first join was handled, and nothing retried a rejoin that got `UNAVAILABLE`, so a reconnecting player stayed unjoined with the choices locked while the socket lived. A follow-up PR retries that join after the backoff in the client and shows it as busy in the store; `web/src/protocol/client.test.ts` ("sends a join that got UNAVAILABLE again after the growing backoff, then resends the unsettled answer") and `web/src/stores/quiz.test.ts` ("UNAVAILABLE on a rejoin after a reconnect: busy until the retried join succeeds on the same socket, with the answer kept") now catch it. A later keyboard pass in real Chromium found another AI mistake in the caret fix: it read the selection in an input listener that ran after the `v-model` listener, and a browser flushes Vue between the two, so each typed key went in at position 1 (`vocab-42` became `V24-BACO`). The happy-dom test dispatched the event from script and could not see it. PR-154 reads the selection in a pre-flush watcher; `web/src/views/JoinView.test.ts` ("keeps the order and the caret of keys typed one by one, also mid-ID") runs the input listeners one at a time with a flush between them and now catches it.
- **Verification:** `make check` (exit 0; vitest 283 passed). New tests in `web/src/views/JoinView.test.ts`, `web/src/components/join/join.test.ts` and `web/src/stores/quiz.test.ts` failed before the fixes (for example `selectionStart` 8 instead of 7, a `SecurityError` from the storage getter) and pass after. `scripts/check_internal.py --commits origin/main..HEAD` (clean).
