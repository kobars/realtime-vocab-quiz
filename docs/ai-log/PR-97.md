## PR-97 — Make the host end wait for the AOF fsync and fix request log context

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Fix four verified defects from the post-merge review of PR #84: the host end skipped the `WAITAOF 1 0 2000` step of the Redis spec, a lost mark still answered 200 `ended` with `endSeq: null`, an unhandled error gave a 500 without `X-Request-ID` and logged its traceback with `request_id: null`, and WebSocket log lines never carried `quiz_id`.
- **Prompt / interaction:** The agent worked from the review's verified finding list, wrote one test per finding, and confirmed that each new test fails on `main` before the fix (the three HTTP and WebSocket tests by stashing the source change; the Redis tests need the new store method).
- **What was wrong or changed:** The host end sequence moved from the HTTP route into one store method, `end_by_host`; the Redis store runs both script calls and `WAITAOF` on one dedicated connection, because `WAITAOF` only counts the writes of the connection that sends it, and redis-py's pool would otherwise send it on any connection. A domain `UNAVAILABLE` code maps to 503. The middleware catches the exception itself, since `call_next` re-raises and the old code never reached the line that set the header. The WebSocket gateway binds the connection id before the receive task starts, so that task inherits it, and the join binds `quiz_id` in that task; the close line rebinds `quiz_id` in the endpoint's own task. During the rebase the protocol table conflicted with a newer `/admin` 404 sentence on `main`; both were kept. A mistake found later: `end_by_host` waited for the fsync only after a fresh mark, so a retry after a failed `WAITAOF`, or a second overlapping host end, found the mark and announced with no fsync of its own. PR #107 fixed it; `api/tests/integration/test_deadline.py::test_a_retry_after_a_failed_fsync_waits_for_its_own_fsync` and `::test_overlapping_host_ends_each_wait_for_the_fsync_before_announcing` now catch it.
