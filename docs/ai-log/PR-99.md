## PR-99 — Fix sender overload, flush deadline and receive loop after close

- **Tool:** Claude Code (claude-opus-5-5)
- **Task:** Fix four confirmed defects of the per-socket sender and the receive loop from the post-merge review of PR-89: the hard-limit path recursing instead of closing 1013, the flush deadline given as an absolute time to a relative timeout, `close()` rescheduling a finished timeout after a failed write, and the receive loop still handling frames while a replaced socket flushes.
- **Prompt / interaction:** The agent got the verified findings with their reproductions, wrote one test per finding against fake sockets and a stub service, confirmed that each test failed on the old code for the reported reason (RecursionError, TimeoutError from the test's wait, `RuntimeError: Cannot change state of finished Timeout`, a `join` handled after the close), then made the fixes.
- **What was wrong or changed:** (1) The first draft of the tests failed `ruff` (unused arguments in the fake socket and the stub service) and `mypy` (the inbound event list was inferred as `dict[str, str]`, so the disconnect code did not fit); both were fixed before the commit. (2) Rebasing onto `main` conflicted in the test file, because a PR merged meanwhile changed `Registry` to take a store and a grace period; the new tests were re-applied on top with `Registry(cast("Store", None), 10_000)`. (3) The receive-loop fix was incomplete: it stopped handling frames once the sender was closing, but a `join` that had already passed that check and was awaiting the store still committed after the newer join, bound the closing socket and closed the newer one, leaving both closed with 4001. PR-123 fixed it with a store fence on `join`; `api/tests/integration/ws/test_connections.py::test_a_replaced_sockets_in_flight_join_does_not_take_the_session_back` and `api/tests/contract/test_store_contract.py::test_a_replaced_connection_cannot_join_back` now catch it. (4) The post-merge review confirmed three more AI mistakes, fixed in PR-114: the writer reset `_in_flight` only after a successful `send_text`, so after a failed write `buffered` still counted the lost frame (now caught by `test_a_failed_write_leaves_only_the_queue_in_the_buffer`); the receive-loop test closed the sender with an empty queue, so the writer was not flushing as its comment said and the result depended on task step order (it now queues a frame the client does not read before the close); and the replaced-socket test ended with a broadcast that returned at once because `replace` had already closed the sender, so the broadcast path the PR names was never run (now `test_a_broadcast_past_the_hard_limit_after_a_failed_write_closes_1013`, which fails with `Cannot change state of finished Timeout` without the deadline reset).
