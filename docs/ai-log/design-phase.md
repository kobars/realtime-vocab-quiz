## Design phase — Draft the architecture and the specs, then review them with a second model

- **Tool:** Claude Code (claude-opus-5-5) drafted the design; Codex CLI (`gpt-6-astra`, high reasoning, read-only sandbox) and a second Claude Code agent (claude-opus-5-5, fresh context, read-only) reviewed it.
- **Task:** Draft the design before any code: the architecture, the WebSocket protocol, the Redis data model and scripts, and the test strategy. Then have a second model review the drafts for real defects, and turn the reviewed drafts into the specs in `docs/spec/` and the ADRs, one file each in `docs/adr/`, indexed by `docs/DECISIONS.md`.
- **Prompt / interaction:** I gave Claude Code the challenge README and a written list of the rules and choices (self-paced quiz, integer scoring, one Redis, two API nodes), and it drafted each part. I then wrote one neutral review prompt (find defects in concurrency, idempotency, time, reconnect and resync, backpressure, load realism and security; quote the draft; no generic advice), with none of my own suspicions in it, and ran Codex and the second Claude agent on it in parallel; I checked every claim against the draft before adopting it.
- **What was wrong or changed:** Five of the defects the reviews found in the drafts, and how the design changed:
  1. **A reconnect created a new player** (both reviewers). Tickets were issued from the display name and were single use, so the only way to get a ticket for a reconnect also made a new user ID; the player's score stayed with the old one. Now `POST /sessions` gives a session token once per tab, and `POST /tickets` with that token gives a fresh single-use ticket for the same user before every connect.
  2. **Retries of `next` or `answer` could skip a question or restart its timer** (both). `next` carried no fields, so a double click or a resend after a lost `question` advanced twice and the unseen question scored 0; a re-serve could also restart the 20 s clock and raise the bonus. Now `next` and `answer` carry the question index, the serve time is stored once and returned on a retry, and an answer and a skip of the same question exclude each other.
  3. **Only the tick checked the deadline, and ticks stop on a node with no sockets** (both). A join or an answer after the deadline could still see the quiz open, and a quiz whose players all left never ended. Now `join`, `serve_question`, `score_answer` and the tick script `publish_leaderboard` compare Redis `TIME` with the deadline and refuse late writes, and the node that gets the refusal runs the idempotent end script. `leave` is still accepted after the deadline: it removes the caller's presence entry and sets no `dirty`.
  4. **The ranking number could overflow, and 0-point answers moved the tie-break** (both). The sorted-set score packs `reachedRelMs` into 22 bits (about 69.9 min) while the quiz window was configurable without a limit, and `reachedAt` changed on every answer, so a wrong answer moved a player down among equals. Now `create_quiz` rejects a window above 60 min, and `reachedRelMs` changes only on an answer that scores.
  5. **Join broadcasts grew with the square of the players** (the second Claude agent). Each new player made the join script increment `seq` and publish, so 5,000 joins meant about 12.5 million sends that could not be dropped. Now a join only sets `dirty`, and the next coalesced `leaderboard` frame carries the player count.

  Not adopted: Codex proposed removing the snapshot cache, because answers do not move `seq` and a cached per-player snapshot could be stale. I narrowed it instead: only the shared standings are cached, per (quiz, `seq`, status, player count), and the player's own row is read fresh. The cached list is the standings as of its read at that `seq`: answers do not move `seq`, so it can lag them until the next tick's frame corrects it, and only the own row is always current. One Codex claim, that the store tests must run on both stores, was already in the draft.
