# Redis spec: keys, scripts and coalescing across nodes

This document is the store design behind the quiz rules. It keeps the consistency contract (domain §8, C1–C6) true when two or more API nodes serve the same quiz against one Redis, with no node owning a quiz. The rules themselves are in `docs/spec/domain.md` and the messages in `docs/spec/protocol.md`; where this file disagrees with the domain spec, the domain spec wins. The decisions are ADR-005 to ADR-008 in `docs/DECISIONS.md`.

## 1. Principles

- **One schema** for scoring and fan-out (ADR-008). Every key of quiz `Q` starts with `quiz:{Q}:`; the braces are a hash tag, so all keys of a quiz live in one Redis Cluster slot and one script may touch all of them.
- **Every write with more than one step is one Lua script** (ADR-005). Redis runs one script at a time, so no interleaving of nodes can see or leave a half-done write. Each script receives every key of the quiz as `KEYS`, in the fixed order of §2, built by one function in the Redis adapter; scripts never build key names themselves.
- **One clock.** Scripts read `TIME` (`now = sec × 1000 + floor(usec / 1000)`, integer ms) for every serve time, answer time, deadline check and reach time. The Python side never passes a time or points to a script. The in-memory store used by unit tests implements the same port with an injected clock (`clock: Callable[[], int]`, ms), which tests advance by hand.
- **The `seq` rule** (C2). Only a script that publishes a broadcast runs `INCR seq`: `publish_leaderboard` and `end_quiz`. `create_quiz`, `join`, `serve_question`, `score_answer`, `leave`, `renew_presence` and `mark_dirty` never increment `seq` and never publish on `events`; they read `seq` for `atSeq`. `join` publishes only on `control`, which carries no `seq` and never reaches a client.
- **The points formula exists once**, in `lua/lib/points.lua`; the loader puts it in front of `score_answer`. The Python twin is checked against it for every elapsed value from −1,000 (a clock step back) to `T + 1`.

## 2. Keys

`Q` is the quiz ID. Hash fields that hold lists are JSON arrays (booleans as `0`/`1`). `uid` is the user ID and `i` a question index; `|` never occurs in a user ID, so it is a safe separator.

| # | Key | Type | Content |
|---|---|---|---|
| 1 | `quiz:{Q}:meta` | hash | `questionCount`, `timeLimitMs`, `windowMs`, `startMs`, `deadlineMs`, `questionIds` (JSON array, in serve order); `endedMs` and `endSeq` are absent until the quiz ends |
| 2 | `quiz:{Q}:key` | hash | the answer key: `i` → the correct choice index. Never leaves Redis except in that player's own `answer_result` |
| 3 | `quiz:{Q}:names` | hash | `uid` → display name (trimmed and normalized) |
| 4 | `quiz:{Q}:present` | hash | `uid` → `[connId, seenMs]`: the player's current connection and when its node last renewed it. `HLEN` is `onlineCount` |
| 5 | `quiz:{Q}:totals` | hash | `uid` → total (integer) |
| 6 | `quiz:{Q}:board` | sorted set | member `uid`, score = the composite of §4. `ZCARD` is `playerCount` |
| 7 | `quiz:{Q}:serve` | hash | `uid` → `[cursor, serveMs, finished]`; `[-1, 0, 0]` after the first join |
| 8 | `quiz:{Q}:subs` | hash | `uid\|submissionId` → the stored reply `[questionIndex, choiceIndex, correctChoiceIndex, correct, late, pointsAwarded, score, atSeq]` |
| 9 | `quiz:{Q}:answered` | hash | `uid\|i` → `[choiceIndex, pointsAwarded, elapsedMs]`, `choiceIndex = -1` for a skip. The field's existence closes question `i` for that player |
| 10 | `quiz:{Q}:seq` | string | the broadcast counter, `0` at creation |
| 11 | `quiz:{Q}:dirty` | string | `1` while the standings or counts changed since the last `leaderboard` frame |
| 12 | `quiz:{Q}:scored` | set | the `uid`s that scored since the last `leaderboard` frame; `publish_leaderboard` reads and deletes it |
| 13 | `quiz:{Q}:replaced` | set | the `connId`s that a newer `join` of their user took over; a `join` from one of them is refused |
| 14 | `quiz:{Q}:tick` | string | the tick token: the publishing node's ID, set with `SET NX PX 200` |
| — | `quiz:{Q}:events` | pub/sub channel | one message per `seq`: `{"frame": <the broadcast JSON (leaderboard or quiz_ended)>, "ranks": [[uid, rank, score], …]}` |
| — | `quiz:{Q}:control` | pub/sub channel | `{"type": "session_replaced", "uid": …, "connId": <the replaced connection>}`; no `seq`, never relayed to a client |

**TTL.** Keys 1–13 are the data keys. They share one TTL, `QUIZ_TTL_MS` = 24 h, and every write script ends by running `PEXPIRE` on all of them, so a quiz expires as a whole 24 h after its last write and is never half there. A key that a script creates gets its TTL in the same script. The tick token keeps its own 200 ms expiry and is never refreshed; `publish_leaderboard` only cuts it back to one tick when a clock step back has stretched it (Redis stores expiry as wall-clock time). The channels are not keys and have no TTL.

**Encoding notes.** Redis Lua's `cjson` encodes an empty table as `{}`, so an empty list is written as the literal `[]`. Lua turns numbers into strings with 14 significant digits, so a composite score is passed to `ZADD` as `string.format('%.0f', s)`, never as a bare number.

## 3. Scripts

All scripts return a flat array whose first element is a status (`ok` or an error code of protocol §7). "Deadline check" means: if `endedMs` is set or `now ≥ deadlineMs`, return `QUIZ_ENDED` plus `endSeq` (or `nil` when no `quiz_ended` was published yet), write nothing, and let the caller run `end_quiz` when `endSeq` is `nil` (§3.1). "Presence check" means: `present[uid]` exists, else `NOT_JOINED`; its `connId` equals the caller's, else `SESSION_REPLACED`; both write nothing. "Refresh" means the TTL step of §2. Every script except `create_quiz` starts with "`meta` exists, else `QUIZ_NOT_FOUND`", so no script creates the keys of a quiz that expired or was lost.

| Script | Inputs (ARGV) | Checks, in order | Writes | Returns | `seq` |
|---|---|---|---|---|---|
| `create_quiz` | `questionIds` (JSON), answer key (JSON), `timeLimitMs`, `windowMs` | `meta` absent, else `INVALID_STATE`; else `INVALID_MESSAGE` unless: `1 ≤ windowMs ≤ 3,600,000` (keeps `reachedRelMs < 2^22`, §4), `1 ≤ questionCount ≤ 100`, the question IDs are unique, `1 ≤ timeLimitMs ≤ 3,600,000` (so the points formula never divides by 0), one answer per question, each `0…3` | `meta` (`startMs = now`, `deadlineMs = now + windowMs`), `key`, `seq = 0`; refresh | `ok, startMs, deadlineMs` | no |
| `join` | `uid`, `displayName`, `connId` | `meta` exists; deadline check; `connId` not in `replaced`, else `SESSION_REPLACED` (nothing written) | First join: `names`, `totals = 0`, `board` with total 0 and `reachedRelMs = max(0, now − startMs)`, `serve = [-1, 0, 0]`. Every join: `present[uid] = [connId, now]`, `SET dirty 1`; if the old `connId` exists and differs from the caller's: `SADD replaced` the old `connId` and `PUBLISH control` `session_replaced` with it; refresh | `ok, atSeq, cursor, cursorOpen, finished, total, questionCount, timeLimitMs, quizRemainingMs, displayName, replacedConnId` (`displayName` is the stored name, so a rejoin under another name gets the first join's name back) (the old `connId`; `nil` when there was none or it equals the caller's) | no |
| `serve_question` | `uid`, `i`, `connId` | `meta` exists; deadline check; `serve[uid]` exists, else `NOT_JOINED`; presence check; then the rows of domain §5.1 in order: `finished = 1` and `i = N` → the `finished` reply; `i = c ≥ 0` → question `c` with the stored `serveMs` (both write nothing); `i = N` → finish from any cursor; `i = c + 1 < N` with `finished = 0` → serve; any other `i` (also `c + 1` once `finished = 1`) → `INVALID_STATE`, nothing written | If question `c` is open: `answered[uid\|c] = [-1, 0, max(0, now − serveMs)]` (skip, 0 points). Then `serve[uid] = [i, now, 0]`, or `[c, serveMs, 1]` for `i = N`; refresh. No `dirty`: a skip changes no standing | `ok, kind (question or finished), i, questionId, remainingMs, atSeq`; for `finished` also `total, rank, playerCount` | no |
| `score_answer` | `uid`, `i`, `choiceIndex`, `submissionId`, `connId` | In domain §5.2 order: `subs[uid\|submissionId]` for the same `i` → the stored reply; for another `i` → `INVALID_MESSAGE`; deadline check; `serve[uid]` exists, else `NOT_JOINED`; presence check; `i > cursor` → `QUESTION_NOT_OPEN`; `answered[uid\|i]` exists → `ALREADY_ANSWERED` | `e = max(0, now − serveMs)` and `stepBack = 1` when `now < serveMs`; points from `points.lua` (0 if wrong or `e > T`); `answered[uid\|i]`; if points > 0: `totals`, `board` with the new total and `reachedRelMs = max(0, now − startMs)`, `SADD scored uid`, `SET dirty 1`; if `i = N − 1`: `finished = 1`; `subs[uid\|submissionId]` = the reply with `atSeq = GET seq`; refresh | `ok`, the 8 fields of the stored reply, `stepBack` (`0` on a replay), `replay` (`1` on a replay). Neither flag is stored, so a replay stays byte-identical | no |
| `publish_leaderboard` | node ID, `tickMs`, `topN`, `fullListMax` | `meta` exists; `endedMs` set or `now ≥ deadlineMs` → `ended, endSeq`; `tick` exists → `busy, PTTL tick` (a PTTL above `tickMs`, left by a clock step back, is first cut to `tickMs` with `PEXPIRE`); `DEL dirty` returns 0 → `clean` | `SET tick <node> NX PX tickMs` (200), `INCR seq`, `PUBLISH events` the frame (`playerCount`, `onlineCount`, every row up to `fullListMax` (200) players, else the top `topN` (50), `rebase: false`) with `ranks` = above `fullListMax` players, `[uid, rank, score]` for each member of `scored` outside the top `topN`, else `[]`; `DEL scored`; refresh | `published, seq` | yes |
| `leave` | `uid`, `connId` | `meta` exists; `present[uid]` holds `connId`, else `stale` (a newer connection took over; nothing is written) | `HDEL present uid`; `SET dirty 1` while the quiz is open; refresh | `ok` or `stale` | no |
| `end_quiz` | reason (`deadline`, `host` or `mark`), `topN` | `meta` exists; `endSeq` set → `ended, endSeq` (idempotent); reason `deadline` and `now < deadlineMs` → `not_due`; reason `mark`, or reason `host` and `endedMs` absent → the mark below | Mark (`mark`, or a first `host` call): `endedMs = min(now, deadlineMs)` if absent, else written again with its value, `DEL dirty`; refresh; returns `marked`. Publish (host with `endedMs` set, or deadline due): `endedMs = min(now, deadlineMs)` if absent, `DEL dirty`, `INCR seq`, `HSET meta endSeq`, `PUBLISH events` the `quiz_ended` frame (top `topN`, `playerCount`, `you: null`) with `ranks: []`; refresh | `marked`, or `ended, endSeq` | yes, once per quiz |
| `renew_presence` | `staleMs`, then pairs `uid`, `connId` | `meta` exists; `endedMs` set or `now ≥ deadlineMs` → `ended`, nothing written | For each pair whose `present[uid]` holds that `connId`: `present[uid] = [connId, now]`. Then `HDEL` every entry with `seenMs < now − staleMs`, and `SET dirty 1` if one was removed; refresh | `ok, removed` | no |
| `mark_dirty` | — | `meta` exists; `endedMs` set or `now ≥ deadlineMs` → `ended, endSeq`, nothing written | `SET dirty 1`; refresh | `ok` | no |

A reconnecting `join` writes no player state (names, totals, board, serve): only the presence and `dirty` change, so the reconnect shows in `onlineCount`. The leave of a disconnected player runs after the 10 s grace, so a reconnect within the grace changes nothing. The compare on `connId` stops a late grace timer on one node from marking offline a player who already reconnected on the other node.

**Session replacement across nodes.** Every node subscribes to `control` beside `events` for each quiz it serves. When a `join` replaces another connection, the script publishes `session_replaced` with the old `connId`, and the node that holds that socket sends `error SESSION_REPLACED` and closes it with 4001 (protocol §7), whichever node it is. Pub/sub delivers at most once, so the store also fences: `serve_question` and `score_answer` take the caller's `connId` and refuse a connection that `present` no longer holds with `SESSION_REPLACED`, writing nothing, so the old tab cannot play on even when the message is lost; its node closes it on that reply. The fence covers `join` too: a replaced connection's own `join`, sent before its node closed it and run after the newer one, gets `SESSION_REPLACED` from the `replaced` set instead of taking the presence back. A repeat `join` on the same connection replaces nothing and publishes nothing.

**Presence after a node dies.** The 10 s grace timer runs on the node that held the socket, so it dies with that node. Each node therefore calls `renew_presence` every 3 s for each quiz it serves, with its own `(uid, connId)` pairs and `staleMs = 13,000` (the grace plus one renew period, so a normal disconnect still leaves through its grace timer first). An entry that no live node renews is dropped by the next `renew_presence` of any other node of the quiz, 13–16 s after its node died, and the next frame carries the lower `onlineCount` (protocol §9). The `connId` compare means a node renews only its own connections, never a newer one on another node.

**Reads at one `seq`.** Reads that must agree with one `seq` (`snapshot`, `leaderboard_page`, `rank_update`) use one read-only script, `read_standings(offset, limit, topN, fullListMax, uid…)`, which returns `seq`, `playerCount`, `onlineCount`, the status, the rows (`limit` 0: a broadcast's rows; −1: none, for a read of the given users alone) and, for each given `uid`, its `rank`, display name and `score` (`nil` if that user is not a player) in one step. A `snapshot` is the exception. The node caches its shared part (the rows, counts and status of one `read_standings` without a `uid`) per quiz, keyed by `seq`, status and `playerCount`. It first reads `snapshot.you` fresh with a `read_standings` of the connection's user alone (`limit` −1), and that read's `seq`, status and `playerCount` select the cached part. On a miss it reads the shared part again (concurrent misses of one quiz share that read); if that read lands at another key, one `read_standings` with the user replaces both. `score_answer` moves no `seq`, so the cached rows can lag answers scored since the cached read, and the list can show an older score or rank than `you` until the next frame corrects it; only `you` is always current (DESIGN §15). A player who scored and is outside a frame's top 50 gets `rank_update` from that frame's `ranks`, so it carries the frame's `seq` as `atSeq` (protocol §4); `score_answer` puts the player in `scored`, and the script that builds the frame computes the ranks. A player whose rank only shifted gets at most one `rank_update` per second, from `read_standings` with the node's players outside the top 50, with that read's `seq` as `atSeq`. Each node relays `frame` to every socket of the quiz and sends `rank_update` only to its own sockets listed in `ranks`.

**Clock step back.** When `score_answer` clamps `e` (`now < serveMs`), it returns `stepBack = 1` after the stored reply, and the scoring service increments `redis_clock_step_total` (domain §2). The flag stays out of the stored reply, so a replay is unchanged and never counts twice. The service counts `answers_total{result}` (`late` if late, else `correct` or `wrong`) only when the trailing `replay` flag is 0, so each answer counts once.

### 3.1 Ending a quiz

The quiz is `ended` from the clock alone (domain §3.1): every write script except `create_quiz`, `leave` and `end_quiz` refuses at `now ≥ deadlineMs` and writes nothing (`leave` still removes the caller's presence entry, and `end_quiz` records the end). Announcing the end is separate, and three paths run the idempotent `end_quiz`; whichever runs first publishes `quiz_ended`, the others get `ended, endSeq`:

1. **The first write after the deadline.** `join`, `serve_question`, `score_answer` and `publish_leaderboard` return `QUIZ_ENDED` (or `ended`) with `endSeq = nil`; the node then calls `end_quiz` with reason `deadline`. The refused script itself never increments `seq`. Before the deadline (a host end that is marked but not announced yet) that call returns `not_due` and the node does nothing more.
2. **A deadline timer** on each node that has sockets for the quiz calls `end_quiz` at `deadlineMs`. It only makes the announcement prompt; correctness never depends on it.
3. **The mock host action** "end now" runs in two steps, so that an announced end survives a Redis restart. `end_quiz(mark)` first only writes the end mark (`endedMs`), and writes it again with the same value when it exists already (a retry, or a second host request that overlaps the first); from then on every write is refused. The node then runs `WAITAOF 1 0 2000` on the same connection (Redis does not allow it inside a script), which covers that write and every earlier one, and only when that reports the local fsync does it call `end_quiz(host)`, which publishes `quiz_ended`. So every host request that can announce has first confirmed the fsync of the mark itself. If the fsync is not confirmed, the host request fails with `UNAVAILABLE` and the host retries; `end_quiz` is idempotent. A mark lost in a crash before its fsync was never announced, so no client saw an end that is then undone. If the node dies between the steps and the host does not retry, writes stay refused and the deadline paths announce the end at `deadlineMs`. The Redis containers of the tests run with `appendonly yes`, so `WAITAOF` works there; the in-memory store has nothing to wait for.

After `endSeq` is set, `publish_leaderboard` never publishes again, so `quiz_ended` is the last broadcast.

## 4. The composite score

```
score        = (2^30 − total) × 2^22 + reachedRelMs
total        = 2^30 − floor(score / 2^22)
reachedRelMs = score mod 2^22
```

`ZRANGE` ascending gives the standings order: a higher total has a smaller first term; equal totals sort by `reachedRelMs`; equal scores sort by member, which Redis compares byte by byte, so ties go to the smaller `userId` in ASCII order. The Python standings code sorts with the same byte order.

Limits:

- `0 ≤ reachedRelMs < 2^22` (4,194,304 ms, about 69.9 min). Writes are refused at `now ≥ deadlineMs`, so `reachedRelMs < windowMs ≤ 3,600,000`; `create_quiz` rejects a larger window. A clock step back is clamped to 0.
- `0 ≤ total < 2^30`. The highest possible total is 150 per question, far below.
- The largest score is below `2^30 × 2^22 + 2^22 = 2^52 + 2^22 < 2^53`, so a double, a Redis sorted-set score and a Lua number all hold it exactly.

## 5. Coalescing across nodes without an owner

No node owns a quiz (ADR-006). Every node that holds at least one socket of quiz `Q` runs the same loop for it:

```
loop while the node has sockets of Q:
    status, value = publish_leaderboard(Q, nodeId)
    if status == "busy":    sleep(value + 1 ms)    # value = the token's PTTL
    elif status == "ended": call end_quiz(Q, "deadline") if value is nil; stop
    elif status == "QUIZ_NOT_FOUND": stop          # the quiz expired, or Redis lost it
    else:                   sleep(200 ms)          # "published" or "clean"
```

The gate is atomic: inside one script the node sees no token, deletes `dirty` (and gets 1) and sets the token. So at most one frame per quiz leaves Redis per 200 ms, whatever the number of nodes, and two nodes ticking at the same instant cannot both publish or skip a `seq`. A node that loses the race sleeps until the token expires, so the next frame goes out as soon as one is allowed.

**Worst-case staleness against C5** (p99 below 500 ms from "answer accepted" to "leaderboard delivered"). `score_answer` sets `dirty` in the same script that accepts the answer. The frame that carries it leaves Redis after at most one token lifetime (200 ms) plus the node's timer lag, then costs one script run (well below 1 ms for 200 rows), one `PUBLISH` to each node, and one write per socket. With a few milliseconds of timer lag the store part is about 200 ms, which leaves about 300 ms for the per-socket writes and the network; the load runs measure the client-observed latency. Cost: each node calls the script about 5 times per second per active quiz.

**Failure cases.**

| Failure | What happens | Clients see |
|---|---|---|
| A node dies before or during its call | The script runs entirely or not at all. If it did not run, `dirty` stays set and another node with sockets of the quiz publishes within about 200 ms. If the dead node held the only sockets, its clients reconnect to the other node, whose first `join` starts the loop there; `dirty` is still set | At most one tick of extra delay; reconnecting clients resync |
| A node dies right after the script | The frame is already published to every node | Only its own clients miss it; they reconnect and resync |
| A node dies holding sockets | Its grace timers die with it, and nothing renews its `present` entries. The next `renew_presence` of another node of the quiz drops them 13–16 s later and sets `dirty` (§3) | `onlineCount` drops within about 16 s; the players reconnect elsewhere and count again |
| Two nodes tick at once | The second one sees the token: `busy` | Nothing |
| Redis restarts (AOF `everysec`) | Up to about 1 s of writes is lost, `seq` may go back, and the token, `dirty` or `endSeq` may be gone. The script cache is empty, so the adapter reloads scripts on `NOSCRIPT`. After the reconnect each node runs `mark_dirty` for each of its quizzes, a script, so `dirty` gets the TTL like any other key; a quiz whose `meta` was lost returns `QUIZ_NOT_FOUND` and the node stops its loop. Then it drops its cached snapshot standings and sends each client a snapshot. A lost deadline end: `end_quiz` runs again, because the deadline is still in `meta`. A host end is never lost once announced, because `quiz_ended` goes out only after `WAITAOF` confirmed the fsync of `endedMs` (§3.1); a mark lost before its fsync was never announced, and the host's retry ends the quiz again | The node's snapshot replaces the standings; `seq < lastSeq` on a broadcast → resync (protocol §3). Only an answer without an `answer_result` yet is sent again (same `submissionId`) and scored, unless the serve of its question was lost too: then the cursor is back before that question, the resend gets `QUESTION_NOT_OPEN`, the client settles it without a score and rejoins, and the question is served anew. An acknowledged answer within the lost second is not resent: the player's total in the snapshot drops back by its points (DESIGN §10), and its `answered` field is lost with it, so the question is open again for that player (served anew instead if its serve was lost too). The player's next `next` closes it as a skip with 0 points; a rejoin before that shows it again (`cursorOpen`), and a new answer is scored from the stored serve time. A lost finish (`finished = 1`) puts a player who saw the result screen back on the last question at the next rejoin. A second `quiz_ended` is applied like the first |
| A node's pub/sub connection drops | Frames published meanwhile do not reach that node. It subscribes again after a full-jitter backoff (protocol §7), also when the Redis client reconnected on its own, and sends each of its clients a snapshot; queued frames that the snapshots already hold are not relayed | The node's snapshot replaces the standings; until then a `seq` gap, or a `pong.seq` above `lastSeq` for 1 s (`pong` reads the counter from Redis), → resync |
| Redis unreachable | Scripts fail before any write; requests get `UNAVAILABLE`; `/readyz` returns 503 | Retries after backoff (`next` and `answer` are safe to repeat) |
